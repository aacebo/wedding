# Phase 02 — Google SSO

## Goal
Let the two planners sign in with Google and authorize read-only access to their
Gmail and Drive, storing tokens securely for later ingestion. Only allowlisted
emails may complete sign-in.

## Scope
- New workspace crate `crates/google` holding OAuth2 + (later) API clients.
- OAuth2 authorization-code flow with offline access (refresh tokens).
- Encrypted per-account token storage + automatic refresh.
- Session established (Phase 01) on successful, allowlisted login.

## OAuth details
- **Scopes:** `openid`, `email`, `profile`,
  `https://www.googleapis.com/auth/gmail.readonly`,
  `https://www.googleapis.com/auth/drive.readonly`.
- **Access type:** `offline`, `prompt=consent` (to guarantee a refresh token).
- Verify `email` is in the allowlist at callback; otherwise clear session and
  return 404/deny.

## Data model (new migration `003_create_google_accounts.sql`)
`google_accounts`:
- `id UUID PK`, `email TEXT UNIQUE NOT NULL`, `google_sub TEXT UNIQUE`,
  `access_token BYTEA` (encrypted), `refresh_token BYTEA` (encrypted),
  `token_expiry TIMESTAMPTZ`, `scopes TEXT`, `created_at`, `updated_at`.
- Tokens encrypted at rest (AES-GCM via `token_encryption_key`).

## Config additions
- `google_client_id`, `google_client_secret`, `google_redirect_uri`,
  `token_encryption_key` — all from env.

## Routes
- `GET /admin/auth/google/login` → redirect to Google consent.
- `GET /admin/auth/google/callback` → exchange code, validate allowlist, persist
  tokens, set session.
- `POST /admin/auth/logout` → clear session.

## Acceptance criteria
- An allowlisted Google account can log in and lands on `/admin`.
- A non-allowlisted account is rejected.
- Tokens persist encrypted; expired access tokens auto-refresh.

## Security notes
- Read-only scopes only. Never log tokens. `state` param prevents CSRF.
