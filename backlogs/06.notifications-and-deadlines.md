# Phase 06 — Notifications & Deadline Reminders

## Goal
Surface upcoming and overdue deadlines so nothing slips. In-page only for now,
but structured so email/push channels can be added later without schema changes.

## Scope
- Derive reminders from `deadlines` (and todos with `due_date`).
- An in-page notifications panel + unread badge, with read/dismissed state.

## Data model (new migration `007_create_notifications.sql`)
`notifications`:
- `id UUID PK`, `kind TEXT` (`deadline_soon`|`deadline_overdue`|`todo_due`),
  `ref_type TEXT`, `ref_id UUID` (the deadline/todo it points at),
  `title TEXT`, `body TEXT`, `due_date TIMESTAMPTZ NULL`,
  `status TEXT` (`unread`|`read`|`dismissed`), `created_at`, `updated_at`.
- `UNIQUE (ref_type, ref_id)` so a given reminder isn't recreated each run and
  its `kind` escalates in place (soon → overdue) rather than duplicating.

## Reminder generation
- A `generate_notifications()` service computes reminders:
  - `deadline_soon`: due within a window (e.g. 14/7/1 days).
  - `deadline_overdue`: past due and not done.
  - `todo_due`: todo with an upcoming/overdue `due_date`.
- Idempotent via the unique constraint; updates existing rows as state changes
  (e.g. soon → overdue).
- Invoked on demand now; wired into the scheduler in Phase 07.

## UI
- Bell icon + unread count in the admin nav (all admin pages).
- Dropdown/panel listing notifications, grouped by upcoming/overdue.
- htmx polling (e.g. every 60s) to refresh the badge + panel.
- Mark-as-read / dismiss actions (htmx PATCH).
- Dashboard highlights the nearest deadlines.

## Routes
- `GET /admin/notifications` → panel fragment (htmx).
- `GET /admin/notifications/count` → unread badge (htmx polling target).
- `PATCH /admin/notifications/{id}` → read/dismissed.
- `POST /admin/notifications/refresh` → run `generate_notifications()`.

## Acceptance criteria
- Deadlines within the window produce notifications; overdue ones escalate.
- Badge updates via polling; mark-read/dismiss persists.
- Refreshing does not duplicate notifications.

## Extensibility (future)
- Adding an email channel = a sender that reads `notifications`; no schema
  change required.
